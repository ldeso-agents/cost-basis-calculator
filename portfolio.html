Portfolio Rewind

Rewind an address to any past date and see what it held: every token balance at that block with its USD value that day, plus every AMM liquidity position broken out into the underlying tokens it was worth. Everything runs in your browser — the Alchemy API key is used directly from this page and never sent anywhere else. Also available: the cost basis calculator and the transaction CSV export.

What is this?

A point-in-time snapshot of one wallet on one chain. Pick an instant and the page reconstructs the position as it stood then: which assets were held, how much of each, what each was worth in USD that day, and how much value was sitting inside liquidity pools rather than in the wallet directly.

Nothing is stored on a server. The page is a static HTML file plus a bundled JavaScript module; the only network calls are made from your browser directly to Alchemy’s public API using the key you paste in.

How it works

  1. The rewind instant (interpreted as UTC) is resolved to an exact block by binary-searching block timestamps — the last block at or before that moment.
  2. Paginated alchemy_getAssetTransfers queries scan the account’s whole history up to that block to work out which token and NFT contracts it has ever touched.
  3. Every balance is then read on-chain at that block (balanceOf, eth_getBalance), batched through Multicall3 where available. Reading real state rather than summing transfers keeps rebasing and yield-bearing tokens correct.
  4. Each held ERC-20 is probed for the shape of an AMM pair (token0(), token1(), getReserves()); each held NFT contract is probed for the shape of a concentrated-liquidity position manager (factory(), positions()). Detection is by contract shape, not by a hardcoded address list, so forks work too.
  5. Daily USD prices for that date come from Alchemy’s Prices API, one request per distinct token — including both sides of every pool.

Liquidity positions

V2-style LP tokens

An LP token balance is a pro-rata claim on the pool’s reserves, so each side is lpBalance × reserve / totalSupply, with all three read at the target block. Covers Uniswap V2, SushiSwap, PancakeSwap V2, Aerodrome and Velodrome. The LP token itself is reported as the position rather than as a plain holding, so nothing is counted twice.

V3-style NFT positions

Concentrated liquidity has no fixed split: the same position is all token0 below its range, all token1 above it, and a mix in between. The page reads positions(tokenId) and the pool’s slot0() price at the target block and applies Uniswap’s own LiquidityAmounts math to get the two amounts, flagging whether the position was in range. Ownership is re-checked with ownerOf at that block, so positions later sold or burned correctly disappear.

Uncollected fees are computed in full from the pool’s fee-growth accumulators, not just the tokensOwed checkpoint, and are shown beneath each side’s amount.

Notes & limitations

  • Historical eth_call needs archive access on the RPC endpoint. Alchemy provides it.
  • LP tokens staked in a gauge or farm (common on Aerodrome and Velodrome) are held by the gauge, not the wallet, so balanceOf reports zero and the position is missed.
  • Prices are sampled at daily granularity; intraday moves are smoothed. Tokens Alchemy does not price are listed with their amounts but excluded from the totals.
  • ERC-1155 balances are discovered but not valued, and plain NFTs are not valued either — only liquidity positions are read from NFT contracts.
  • Assets that arrived without a transfer event are invisible to the discovery scan; paste those contracts into extra token addresses.
  • The full-history scan makes the first run slow for very active wallets.
  • Forks whose position manager uses a different positions() layout are skipped with a note rather than reported wrongly.
